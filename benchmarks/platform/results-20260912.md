# Native and browser benchmark, 2026-09-12

The pre-Wasm native release and current native build completed 22/22 runs each; the current browser build completed 19/22. This two-repeat screen found no consistent native slowdown. Completed longer browser workloads took about 1.85-3.01 times as long as current native. The user accepted this as the current web performance tradeoff. It does not establish an unavoidable Wasm penalty or promote a new solver optimization.

## Measured inputs

- Native reference: release 1.0.0, `0b60d36bce6e0554804a6e6c7a9b7cb21ebdbd6e`.
- Current native/browser source: `6e9df0d86d3628d8125243613d075bf699fe1030` plus the frozen benchmark harness.
- Ryzen 9 7950X3D, 16 cores / 32 logical processors, Windows Balanced power plan, full available CPU mask. Affinity was not pinned and other applications were not monitored.
- Chrome 152.0.7977.84; native and Wasm cvc5 1.3.4 identify source commit `f3b21c4`.
- 66 sequential runs, 22 matched triples, two reversed-order repetitions. Five configurations used 8 and 16 workers; case 97 used 16.
- Recorded duration: 70 minutes 14 seconds, 2026-09-12 17:45:23-18:55:37 UTC. The directory timestamp is an identifier, not the authoritative start time.

## Adverse samples and incomplete proofs

- Case 10, 16 workers: native repeat 1 changed -0.46%; repeat 2 changed +19.4% (+3.68 s).
- Case 258, 8 workers: native repeat 1 changed -0.93%; repeat 2 changed +13.4% (+5.06 s).
- Neither met the frozen signal rule: both repetitions over +10% and +0.5 s. Two repetitions cannot rule out a smaller regression; retain both adverse samples for future confirmation.
- Web case 258, 8 workers, repeat 1 stopped at 120 s with two retained layouts. Its other repetition completed in 88.096 s.
- Web case 97, 16 workers, stopped at 600 s in both repetitions with 813 retained layouts each; current native completed in 468.032 s and 374.594 s.

All three capped collections match completed native collections, including their canonical graphs and exact flows. They retain a proven minimum N of 9, but `minimumLinkCount` is null and `enumerationComplete` is false. Matching layouts do not establish a finished proof. Case 97 first witnesses arrived in 3.131 s and 3.325 s; final-layout arrival was not timestamped, so time spent exclusively on remaining proof cannot be calculated. Browser allocated Wasm heaps peaked at 1.69 and 1.99 GiB on these two runs; this is not total browser memory and has no corresponding native process-tree measurement.

## Validation and limits

Analysis rechecked 850 frozen hashes, revalidated all 66 raw records with the frozen Rust verifier, reproduced the original summary exactly, and checked that owned solver runs did not overlap. There were 52 completed-result comparisons across variants and repetitions, plus equality checks of the three partial collections. No witness or result-state mismatch and no run failure was found. This does not replay an exhaustive solve or an SMT proof certificate.

Native timings cover the production solve API used by Tauri, backend startup and cleanup. Browser timings cover job admission, worker/module startup, local asset fetch, durable collection appends and worker termination. Chrome launch/navigation, Tauri IPC/UI, SQLite history, full browser history metadata persistence, graph rendering and post-run comparison are outside solve timing. No warm-up solves were used; root traces were disabled. The result is a production solve-path comparison, not an isolated Wasm CPU measurement or an installed-app click-to-render benchmark.

Future work can confirm native case 10 at 16 workers and case 258 at 8 workers, then diagnose browser proof completion on cases 97 and 258. Worker scaling is workload dependent: 16 workers improved cases 36 and 115, but case 10 was slightly slower. No new benchmark is authorized by this record.
